## O que decidimos nesta iteração

1. **Usar PostgreSQL 16 no piloto e no CI.** O PR #10 migrou a conexão para `pg`, manteve as consultas atrás de `src/db.js`/`src/repositorio.js` e configurou o serviço PostgreSQL no workflow. A razão registrada foi validar os mesmos comportamentos contra o banco da Unidade 3; o check `build-e-testes` desse PR aparece como `success`.
2. **Confirmar a retirada com uma atualização condicional por status e ONG.** O repositório só conclui uma doação ainda `aceita` pela ONG correspondente, evitando que outra ONG ou uma segunda confirmação sobrescreva o resultado; essa condição é coberta por testes.
3. **Manter os estados `aceita`/`concluida` do código.** A análise documenta essa correspondência para `RESERVADA`/`CONCLUÍDO`; não alteramos os critérios nem o histórico para trocar a nomenclatura.

## O que funcionou

- O histórico dos PRs #9 e #10 deixa rastros verificáveis de uma correção na contagem mensal e da migração para PostgreSQL.
- O workflow atual usa PostgreSQL 16; o check `build-e-testes` consultado no PR #10 concluiu com sucesso.
- `npm test` local terminou com 17 testes aprovados contra PostgreSQL 16.
- O smoke HTTP local percorreu publicação, aceite, pendência, confirmação, histórico e erro de validade, além de conferir a rota de saúde.
- Os testes em `tests/doacoes.test.js` e `tests/interface.test.js` exercitam as regras e mensagens adicionadas.

## O que mudaríamos

- Atualizar o README na mesma mudança que troca o banco. Ele ainda descrevia SQLite como banco atual e as regras/repositório como por implementar, divergindo do código de `main`.
- Testar também a interface num navegador real; os testes de UI desta iteração executam o script com DOM simulado.
- A identidade da ONG ainda vem de um nome enviado pelo cliente; autenticação não foi adicionada e precisa continuar explícita como limitação.
